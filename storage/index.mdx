Your media stays in your bucket. Connect it once and jobs read private inputs from it and write outputs back to it, addressed through a short id you choose:

```text
storage://<connection-id>/<path>
```

Nothing in the bucket needs to be public. This page is everything true of every connection. Each provider then has its own page for getting a credential.

## Providers

Four kinds connect, and each accepts more than one sort of credential.

| Provider | Credentials it takes |
|---|---|
| [Cloudflare R2](/storage/cloudflare-r2) | An R2 API token, or an access key and secret |
| Amazon S3 | A one-click IAM role, or access keys. Either can be read-only |
| Supabase Storage | Sign in to Supabase, or bring S3 keys |
| S3-compatible | An endpoint, a region and a key pair. MinIO, Backblaze B2, Wasabi |

Anything that speaks the S3 API works through the last row, whether or not it is listed by name.

## How a connection works

A connection is a bucket, a credential, and the id you file them under. The id is the only part a job ever names.

```text
  your bucket                                Rendobar job
  -----------                                ------------

  raw/clip.mp4   ---- input ------------->   downloads it privately
                                                    |
                                                  ffmpeg
                                                    |
  exports/...    <--- destination --------   uploads the output
```

Reading and delivering both go over the same credential. A job never receives it, and no input is ever made public: Rendobar signs a time-limited GET against your bucket when the job dispatches, and the runner streams from that.

### The id

You pick it when you connect, and Rendobar suggests one from the bucket name. It must match `[a-z0-9-]{2,40}`.

It is the only public handle for the bucket, which is the point. Because payloads name the id and never the credential, [rotating a credential](#rotating-a-credential) changes nothing in code you have already written.

### Using it in a job

`storage://` works anywhere a job takes a file URL, on both sides:

```typescript
import { createClient } from "@rendobar/sdk";

const client = createClient({ apiKey: process.env.RENDOBAR_API_KEY });

const job = await client.jobs.run({
  type: "ffmpeg",
  inputs: { source: "storage://demo-bucket/raw/clip.mp4" },
  params: {
    command: "ffmpeg -i source -vf scale=1280:-2 -c:v libx264 -crf 23 -c:a copy out.mp4",
  },
  destinations: ["storage://demo-bucket/exports"],
});
```

The same references work from the [SDK](/sdk), the [CLI](/cli) and the [MCP server](/mcp-server).

### What happens when you connect

Rendobar never saves a credential it has not proven. Before the connection exists, it:

1. Writes a temporary test object
2. Reads it back
3. Lists the bucket
4. Deletes the test object

All four must pass. A failure names the field or permission that caused it rather than forwarding whatever the bucket said, so the dialog can tell you which one to fix.

You can re-run the same four checks on a live connection at any time, from the dashboard or with `client.storage.test(id)`.

## Where outputs land

A destination in the job payload wins. `storage://demo-bucket/exports` writes to `exports/{job_id}.{ext}`, and a bare `storage://demo-bucket` writes to `rendobar/{job_id}.{ext}`.

Everything else is per connection. Open one in [**Storage**](https://app.rendobar.com/storage) and click the pencil on the **Delivery** card.

### Output path

The output path is a template: an object key with `{tokens}` in it. Four tokens exist.

| Token | Becomes |
|---|---|
| `{job_id}` | The job's id, such as `job_ee14ffeecc3f4a1b` |
| `{ext}` | The output's extension, without the dot |
| `{source_name}` | The input file's name, without the extension |
| `{date}` | The UTC date, `YYYY-MM-DD` |

A new connection gets **By date**, which for `raw/clip.mp4` renders like this:

```text
rendobar/{date}/{source_name}.{ext}   ->  rendobar/2026-09-12/clip.mp4
```

That reads well in a bucket listing, and it can collide. **Flat** drops the date:

```text
rendobar/{source_name}.{ext}          ->  rendobar/clip.mp4
```

**Custom template** takes anything you type. Include `{job_id}` and the key can never collide, because the id is unique per job:

```text
rendobar/{job_id}                     ->  rendobar/job_ee14ffeecc3f4a1b.mp4
```

### Name conflicts

A template without `{job_id}` will eventually produce a key that already exists. **Name conflicts** decides what happens then.

**Keep both** appends the last six characters of the job id to the name:

```text
clip.mp4      ->  clip-4a1b6e.mp4
```

**Replace** overwrites the object already at that key.

<Warning>
**Replace** is destructive and Rendobar cannot undo it. The previous object is gone unless the bucket has versioning on. Use it only where the bucket is a cache or a mirror of something you still hold elsewhere.
</Warning>

### Default destination

Turn this on and every job that names no `destinations` delivers here. One connection per organization can hold it, so switching it on elsewhere moves it. Jobs that do name `destinations` ignore it and go where they were told.

### Public URL

Optional. Leave it blank and a delivered file's `url` points at Rendobar. Set it and the `url` points at your host instead:

```text
https://media.example.com/exports/job_ee14ffeecc3f4a1b.mp4
```

It must be `https`, and it cannot be a private or internal host. A private bucket has no public link, so leave the field blank and keep using it. The bucket still works for both inputs and outputs, and only the returned `url` differs.

### Reading the result

A completed job carries one `deliveries[]` entry per destination.

```json
{
  "deliveries": [
    {
      "storage": "demo-bucket",
      "status": "delivered",
      "path": "exports/job_ee14ffeecc3f4a1b.mp4",
      "url": "https://media.example.com/exports/job_ee14ffeecc3f4a1b.mp4"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `storage` | The connection id it was delivered through |
| `status` | `pending`, `delivered` or `failed` |
| `path` | The object key written, after the template and any rename |
| `url` | Your public URL when one is set, otherwise a Rendobar one |
| `reason` | Present only on `failed`. See below |
| `renamed` | `true` when the name was taken and **Keep both** freed it |

`deliveries` appears on `GET /jobs/{id}`, not on the list endpoint, and is absent when the job had no destinations.

### When a delivery fails

A failed delivery carries a `reason`. This is the whole vocabulary, and it is the same for every provider.

| Reason | What happened | Fix |
|---|---|---|
| `destination_denied` | The credentials may not do this on the bucket or path | Widen the credential to read and write objects, and check it covers this bucket |
| `signature_mismatch` | The destination rejected the signature | Check the access key, the secret and the region, or issue a new credential |
| `bucket_not_found` | No bucket by that name at this endpoint | The bucket was renamed or deleted. Reconnect against the current name |
| `already_exists` | An object already sits at that path | Add `{job_id}` to the output path, or set name conflicts to **Keep both** |
| `object_too_large` | The output exceeds the destination's single-upload limit | Nothing to change on the connection. The output itself is too big |
| `destination_unavailable` | The bucket returned 429 or 5xx, or did not answer | Retried automatically. Retry by hand from the job if it stays failed |
| `not_deliverable` | The job produced no file to deliver | Expected for data-only jobs such as `ffprobe` |

[Error codes](/support/errors) lists the codes a connection can return at connect time.

## Security

Rendobar stores the S3 access key and secret for the bucket, sealed with AES-256-GCM before they reach the database. No endpoint returns them, including to you.

Where a provider issues a richer credential than an S3 pair, that credential is used once to derive the pair and is then discarded. A Cloudflare R2 API token works this way.

### Rotating a credential

Replace the credential on the existing connection, in the dashboard or with `client.storage.update(id, ...)`. The four access checks run again before the new one is accepted.

The id does not change, so every `storage://<id>/<path>` reference you have already written keeps working. This is the reason the id exists.

### Revoking access

Revoke at the provider, not here. Delete the token, key or role in their console and the connection stops working immediately. Each provider page has the exact path.

Deleting the Rendobar connection also ends access, but it does not invalidate the credential itself. If the credential might be held anywhere else, revoke it at the provider too.

## From code

| Method | Does |
|---|---|
| `client.storage.list()` | Every connection in the organization |
| `client.storage.get(id)` | One connection |
| `client.storage.create(params)` | Connect a bucket. Fails validation if the probe fails, conflict if the id is taken |
| `client.storage.update(id, params)` | Rotate the credential, or set the public URL |
| `client.storage.test(id)` | Re-run the four access checks |
| `client.storage.listObjects(id, params)` | Browse folders and objects in the bucket |
| `client.storage.stats(id)` | Delivery activity for the connection |
| `client.storage.delete(id)` | Remove the connection. Does not touch the bucket |

No method returns a stored credential.
