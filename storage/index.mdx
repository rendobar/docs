A storage connection is a bucket you own, a credential for that bucket, and an id that you choose. Jobs read input files from a connected bucket and write their outputs back to it.

By default, Rendobar stores job outputs on its own infrastructure and returns a temporary URL. A storage connection changes where those outputs are written, and allows jobs to read files that are not publicly accessible.

Once a bucket is connected, you reference objects in it with a `storage://` URI:

```text
storage://<connection-id>/<path>
```

This page covers behavior that is the same for every connection. Each provider has its own page describing the credentials it accepts.

## Supported providers

Rendobar connects to four kinds of storage. Each one accepts more than one type of credential.

| Provider | Credentials |
|---|---|
| [Cloudflare R2](/storage/cloudflare-r2) | An R2 API token, or an access key and secret |
| Amazon S3 | A one-click IAM role, or an access key and secret. Either can be read-only |
| Supabase Storage | A Supabase sign-in, or S3 access keys |
| S3-compatible | An endpoint, a region, and an access key pair |

Use **S3-compatible** for any service that implements the S3 API, including MinIO, Backblaze B2, and Wasabi.

## How storage connections work

Jobs reference a connection by its id. They never receive the credential.

<Frame caption="A job reads its input through a signed, time-limited request and writes its output back over the same credential.">
  <img src="/images/storage/diagram-flow.png" alt="Four steps left to right: your bucket, a signed time-limited request, the job running, and the output written back to your bucket" />
</Frame>

When a job is dispatched, Rendobar signs a time-limited GET request against your bucket, and the runner streams the input file from that URL. Outputs are written back with the same credential. No object in the bucket is made public at any stage.

### Connection IDs

You set the id when you connect a bucket, and Rendobar suggests one based on the bucket name. An id must match `[a-z0-9-]{2,40}`.

The id appears in every `storage://` URI, so job payloads never contain credentials. You can [rotate a credential](#rotate-a-credential) without changing any code that references the bucket.

<Frame caption="A storage URI: the scheme, the connection id, and the object key within the bucket.">
  <img src="/images/storage/diagram-uri.png" alt="The reference storage://demo-bucket/raw/clip.mp4 broken into three labelled parts: the scheme, the connection id you chose, and the object key in the bucket" />
</Frame>

### Reference a bucket in a job

A `storage://` URI is valid anywhere a job accepts a file URL. Use it in `inputs` to read an object, and in `destinations` to write the output:

```typescript
import { createClient } from "@rendobar/sdk";

const client = createClient({ apiKey: process.env.RENDOBAR_API_KEY });

const job = await client.jobs.run({
  type: "ffmpeg",
  inputs: { source: "storage://demo-bucket/raw/clip.mp4" },
  params: {
    command: "ffmpeg -i source -vf scale=1280:-2 -c:v libx264 -crf 23 -c:a copy out.mp4",
  },
  destinations: ["storage://demo-bucket/exports"],
});
```

The same URIs work from the [SDK](/sdk), the [CLI](/cli), and the [MCP server](/mcp-server).

### Access checks

Rendobar verifies a credential before it saves a connection. It performs four operations against the bucket:

1. Write a temporary test object.
2. Read the object back.
3. List the bucket.
4. Delete the test object.

All four must succeed. If one fails, Rendobar does not create the connection, and the response identifies the field or permission responsible.

To run the same checks against an existing connection, select **Test Connection** from the connection's actions menu in [**Storage**](https://app.rendobar.com/storage), or call `client.storage.test(id)`.

## Configure output delivery

A `destinations` value in the job payload takes precedence over the connection settings. `storage://demo-bucket/exports` writes to `exports/{job_id}.{ext}`, and `storage://demo-bucket` writes to `rendobar/{job_id}.{ext}`.

To change the connection defaults:

1. In [**Storage**](https://app.rendobar.com/storage), select a connection.
2. On the **Delivery** card, select the edit icon.

### Output path

The output path is a template. Rendobar replaces each token when the job completes.

| Token | Value |
|---|---|
| `{job_id}` | The job id, for example `job_ee14ffeecc3f4a1b` |
| `{ext}` | The output file extension, without the dot |
| `{source_name}` | The input file name, without its extension |
| `{date}` | The UTC date, in `YYYY-MM-DD` format |

New connections use **By date**.

<Frame caption="The By date template and the object key it produces for an input file named clip.mp4.">
  <img src="/images/storage/diagram-template.png" alt="The template rendobar/{date}/{source_name}.{ext} with each token mapped to its value, and the resulting key rendobar/2026-09-12/clip.mp4" />
</Frame>

Three options are available:

| Option | Template | Example output |
|---|---|---|
| **By date** | `rendobar/{date}/{source_name}.{ext}` | `rendobar/2026-09-12/clip.mp4` |
| **Flat** | `rendobar/{source_name}.{ext}` | `rendobar/clip.mp4` |
| **Custom template** | Any value you enter | |

A template that contains `{job_id}` cannot produce a duplicate object key, because job ids are unique.

### Name conflicts

A template without `{job_id}` can produce an object key that already exists in the bucket. **Name conflicts** determines what Rendobar does in that case.

| Setting | Behavior |
|---|---|
| **Keep both** | Appends the last six characters of the job id to the file name. `clip.mp4` is written as `clip-4a1b6e.mp4` |
| **Replace** | Overwrites the existing object |

<Warning>
**Replace** permanently overwrites the existing object. Rendobar cannot recover it unless the bucket has versioning turned on.
</Warning>

### Default destination

When **Default destination** is on, jobs that do not specify `destinations` write their outputs to this connection. One connection per organization can be the default destination, so turning it on for a second connection turns it off for the first.

Jobs that specify `destinations` are not affected.

### Public URL

By default, the `url` field of a delivery points to Rendobar. Set a public URL on the connection to return links on your own host instead:

```text
https://media.example.com/exports/job_ee14ffeecc3f4a1b.mp4
```

The value must be an `https` URL, and it cannot resolve to a private or internal host. Leave the field empty for a private bucket. A private bucket works normally for both inputs and outputs, and only the returned `url` differs.

## Delivery results

A completed job includes one `deliveries[]` entry for each destination.

```json
{
  "deliveries": [
    {
      "storage": "demo-bucket",
      "status": "delivered",
      "path": "exports/job_ee14ffeecc3f4a1b.mp4",
      "url": "https://media.example.com/exports/job_ee14ffeecc3f4a1b.mp4"
    }
  ]
}
```

| Field | Description |
|---|---|
| `storage` | The id of the connection used |
| `status` | `pending`, `delivered`, or `failed` |
| `path` | The object key written, after the template is applied |
| `url` | The connection's public URL when one is set, otherwise a Rendobar URL |
| `reason` | The failure reason. Present only when `status` is `failed` |
| `renamed` | `true` when **Keep both** appended a job id suffix |

A delivered job returns two URLs for the same content. `output.file.url` is a Rendobar URL that expires at `output.expiresAt`. The `url` in `deliveries[]` points to the copy in your own bucket, which does not expire and which Rendobar does not modify after writing it.

Deliveries are also asynchronous. A job can reach `complete` with its `output` populated while a delivery is still `pending`, and a delivery that fails does not change the status of the job. Rendobar sends a `job.delivered` or `job.delivery_failed` [webhook](/guides/webhooks) for each destination, and `POST /jobs/{id}/deliveries/retry` queues the failed deliveries again.

`deliveries` is returned by `GET /jobs/{id}`. It is not included in the job list response, and it is absent when the job specified no destinations.

## Delivery errors

A failed delivery includes a `reason`. Rendobar does not forward error text from the bucket, so the following table is the complete set of values.

| Reason | Description | Fix |
|---|---|---|
| `destination_denied` | The credential is not permitted to perform this operation on the bucket or path | Grant the credential read and write access to objects, and confirm that it covers this bucket |
| `signature_mismatch` | The bucket rejected the request signature | Check the access key, the secret, and the region, or issue a new credential |
| `bucket_not_found` | No bucket with that name exists at the endpoint | The bucket was renamed or deleted. Reconnect using the current name |
| `already_exists` | An object already exists at that key | Add `{job_id}` to the output path, or set name conflicts to **Keep both** |
| `object_too_large` | The output exceeds the destination's single-upload limit | Reduce the size of the output. The connection does not need to change |
| `destination_unavailable` | The bucket returned a 429 or 5xx response, or did not respond | Rendobar retries automatically. Retry manually from the job if it remains failed |
| `not_deliverable` | The job produced no file to deliver | Expected for jobs that return data only, such as `ffprobe` |

For errors returned when you create a connection, refer to [error codes](/support/errors).

## Credential storage

Rendobar stores the S3 access key and secret for the bucket, encrypted with AES-256-GCM before they are written to the database. No API endpoint returns them.

Some providers issue a credential that is not an S3 key pair. Rendobar uses it once to derive the key pair, then discards it. Cloudflare R2 API tokens work this way.

### Rotate a credential

To replace a credential on an existing connection, select **Replace Keys** from the connection's actions menu in [**Storage**](https://app.rendobar.com/storage), or call `client.storage.update(id, ...)`. Rendobar runs the four access checks against the new credential before it accepts it.

The connection id does not change, so existing `storage://<id>/<path>` references continue to work.

### Revoke access

To revoke access, delete the token, key, or role in the provider's console. The connection stops working immediately. Each provider page gives the location.

Deleting a Rendobar connection also ends access, but it does not invalidate the credential itself. If the credential is stored anywhere else, revoke it at the provider as well.

## Available API methods

| Method | Description |
|---|---|
| `client.storage.list()` | Lists every connection in the organization |
| `client.storage.get(id)` | Returns one connection |
| `client.storage.create(params)` | Connects a bucket. Returns a validation error if the access checks fail, or a conflict error if the id is taken |
| `client.storage.update(id, params)` | Rotates the credential, or sets the public URL |
| `client.storage.test(id)` | Runs the four access checks again |
| `client.storage.listObjects(id, params)` | Lists folders and objects in the bucket |
| `client.storage.stats(id)` | Returns delivery activity for the connection |
| `client.storage.delete(id)` | Removes the connection. The bucket is not modified |

No method returns a stored credential.
