Connect an R2 bucket to use private files as job inputs and deliver job outputs straight back to it. Once connected, reference any object in it with:

```text
storage://<connection-id>/<path>
```

Your files never need to be public. Rendobar signs each request against the bucket when a job runs.

**What you'll do:**

1. Open the connect dialog in Rendobar and see what it asks for
2. Create the credential in Cloudflare
3. Connect the bucket
4. Use it in a job

## How it works

A storage connection is a bucket plus its credentials, under a short id you choose. That one connection serves both directions.

```text
  your R2 bucket                             Rendobar job
  --------------                             ------------

  raw/clip.mp4   ---- input ------------->   downloads it privately
                                                    |
                                                  ffmpeg
                                                    |
  exports/...    <--- destination --------   uploads the output
```

The id is what job payloads name, never the credentials. Rotate the credential later and every existing payload keeps working unchanged.

## 1. Open the connect dialog

Start in Rendobar, not in Cloudflare. Open [**Storage**](https://app.rendobar.com/storage), click **Connect Storage**, and choose **Cloudflare R2**.

<Frame caption="Four providers. R2, Supabase Storage and Amazon S3 each take their own credential. Anything else that speaks the S3 API goes through S3-compatible.">
  <img src="/images/storage/connect-providers.png" alt="The Connect Storage dialog with four providers: Cloudflare R2, Supabase Storage, Amazon S3 and S3-compatible" />
</Frame>

The dialog opens on a **Key type** switch, because R2 accepts two kinds of credential:

| Key type | Take it when | Fields |
|---|---|---|
| **API token** | You have none yet. Shortest path | The token, the bucket name |
| **Access key and secret** | You already hold an S3 pair | Account ID, bucket, key id, secret |

Both end in the same place: a stored S3 key pair. The token path just derives one for you.

## 2. Create the credential

### Option A: an R2 API token

R2 speaks the [S3 API](https://developers.cloudflare.com/r2/api/s3/api/), but its credentials come from an [R2 API token](https://developers.cloudflare.com/r2/api/tokens/), not an IAM user. In a second tab:

1. Open **R2 Object Storage**, then **Manage API tokens**, then **Create Account API token**.
2. Under **Permissions**, choose **Object Read & Write**.
3. Under **Specify bucket(s)**, choose **Apply to specific buckets only** and pick the one bucket.

Not Admin. Rendobar reads, writes, lists and deletes objects. It never needs to create or delete a bucket, and Admin grants both.

<Frame caption="Object Read and Write, scoped to one bucket. Admin Read and Write would also let the token delete buckets.">
  <img src="/images/storage/r2-token-scope.png" alt="Cloudflare's Create Account API Token page with Object Read and Write selected and a single bucket chosen" />
</Frame>

Click **Create Account API Token**. Cloudflare shows the token value once.

<Frame caption="The token value. Cloudflare shows it exactly once, so copy it before leaving the page.">
  <img src="/images/storage/r2-token-created.png" alt="The created token page in Cloudflare, with the token value shown once" />
</Frame>

<Warning>
Leave that page without copying and the token is gone. Cloudflare cannot show it again, and you will have to create another.
</Warning>

### Option B: an access key and secret

Take this if you already hold an S3 pair for the bucket. It needs three things instead of one. The **Account ID** is 32 hex characters, from the R2 overview page. Then the access key id and the secret. Rendobar builds the R2 endpoint from the account id.

<Frame caption="The key pair path. Account ID, bucket, then the pair, with the endpoint derived from the account id.">
  <img src="/images/storage/r2-dialog-keys.png" alt="The Cloudflare R2 connect dialog on the access key and secret tab, with the account ID, access key ID and secret masked" />
</Frame>

## 3. Connect the bucket

Back in Rendobar, paste the credential and type the bucket name. On the token path you can paste the whole Cloudflare token page instead of the single value. Rendobar picks the token out of it and fills the provider at the same time.

<Frame caption="Pasting the whole token page fills both fields.">
  <img src="/images/storage/r2-dialog-filled.png" alt="The Cloudflare R2 connect dialog with the API token masked and the bucket name filled in" />
</Frame>

Under **More options**, **id** is the short name the bucket answers to. It is the only public handle, it appears in every `storage://` reference, and it must match `[a-z0-9-]{2,40}`. Rendobar suggests one from the bucket name.

Click **Connect**. Before saving, Rendobar proves the credential actually works:

1. Writes a temporary test object
2. Reads it back
3. Lists the bucket
4. Deletes the test object

The connection saves only if all four pass, and an R2 API token is dropped once the S3 pair is derived from it. If the bucket does not exist, the dialog says so and offers **Create the bucket and connect**.

<Frame caption="Connected. Write, read, list and delete all passed, and the snippets are the exact strings a job takes.">
  <img src="/images/storage/r2-connected.png" alt="The finish screen showing write, read, list and delete all passing, with copyable source and destinations snippets" />
</Frame>

`client.storage.list()` returns the same connections from code.

## 4. Use it in a job

Read an input by putting a `storage://` reference anywhere a job takes a file URL:

```ts
inputs: { source: "storage://demo-bucket/raw/clip.mp4" }
```

Deliver the output by naming the same connection in `destinations`:

```ts
destinations: ["storage://demo-bucket/exports"]
```

Together, in a runnable job:

<CodeGroup>

```typescript SDK
import { createClient, outputUrl } from "@rendobar/sdk";

const client = createClient({ apiKey: process.env.RENDOBAR_API_KEY });

const job = await client.jobs.run({
  type: "ffmpeg",
  inputs: { source: "storage://demo-bucket/raw/clip.mp4" },
  params: {
    command: "ffmpeg -i source -vf scale=1280:-2 -c:v libx264 -crf 23 -c:a copy out.mp4",
  },
  destinations: ["storage://demo-bucket/exports"],
});

console.log(outputUrl(job));
console.log(job.deliveries);
```

```bash cURL
curl https://api.rendobar.com/jobs \
  -H "Authorization: Bearer $RENDOBAR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "type": "ffmpeg",
    "inputs": { "source": "storage://demo-bucket/raw/clip.mp4" },
    "params": {
      "command": "ffmpeg -i source -vf scale=1280:-2 -c:v libx264 -crf 23 -c:a copy out.mp4"
    },
    "destinations": ["storage://demo-bucket/exports"]
  }'
```

</CodeGroup>

That writes `exports/job_ee14ffeecc3f4a1b.mp4`, because a folder destination names outputs by job id so they cannot collide. [Delivery settings](/storage/deliveries) covers naming them yourself, name conflicts, default destinations and public URLs.

`storage://` works anywhere a URL does, including from the [SDK](/sdk), the [CLI](/cli) and the [MCP server](/mcp-server). The [quickstart](/quickstart) covers the job shape itself.

## When a delivery fails

A failed delivery carries a `reason`. These are the whole vocabulary, and nothing the bucket said is ever forwarded.

| Reason | What happened | Fix |
|---|---|---|
| `destination_denied` | The credentials may not do this on the bucket or path | Widen the token to Object Read & Write, or check it covers this bucket |
| `signature_mismatch` | The destination rejected the signature | Re-create the credential. An R2 token cannot be edited into a different scope |
| `bucket_not_found` | No bucket by that name at this endpoint | The bucket was renamed or deleted. Reconnect against the current name |
| `already_exists` | An object already sits at that path | Add `{job_id}` to the output path, or set name conflicts to **Keep both** |
| `object_too_large` | The output exceeds the single-upload limit | Nothing to change on the connection. The output itself is too big |
| `destination_unavailable` | R2 returned 429 or 5xx | Retried automatically. Retry by hand from the job if it stays failed |
| `not_deliverable` | The job produced no file to deliver | Expected for data-only jobs such as `ffprobe` |

[Error codes](/support/errors) lists the codes a connection can return at connect time.

## Security

Rendobar stores the S3 access key and secret, sealed with AES-256-GCM before they reach the database. No endpoint returns them, including to you. An R2 API token you pasted is used once to derive the pair and is then discarded.

Job inputs are never made public. Rendobar presigns a GET against your bucket at dispatch, the runner streams it, and the output goes back over the same credential.

### Rotate a credential

Because jobs name the connection id and not the credentials, rotation changes nothing in your payloads. Replace the credential on the existing connection, in the dashboard or with `client.storage.update(id, ...)`, and the same `storage://<id>/<path>` references keep working. Rendobar re-runs the four access checks before it accepts the new one.

### Revoke access

Revoking is a Cloudflare action, not a Rendobar one. Delete the token in [**R2 → Manage API tokens**](https://developers.cloudflare.com/r2/api/tokens/) and the connection stops working immediately.

<Note>
Deleting the bucket does not revoke the token. They are separate Cloudflare resources, and a token scoped to "all buckets in this account" still reaches every other bucket you own. Scope tokens to one bucket.
</Note>
