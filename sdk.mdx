`@rendobar/sdk` is the official TypeScript client. It wraps the REST API with typed methods, automatic retries, and response unwrapping.

## Install

```bash
npm install @rendobar/sdk
```

The package ships ESM with full type declarations. It runs on Node 18+, Deno, Bun, Cloudflare Workers, and the browser.

## Quickstart

Create a client, submit a job, wait for it to finish, then read the output URL.

```ts title="render.ts"
import { createClient, outputUrl } from "@rendobar/sdk";

const client = createClient({ apiKey: "rb_YOUR_KEY" });

const created = await client.jobs.create({
  type: "ffmpeg",
  params: {
    command: "ffmpeg -i https://example.com/input.mp4 -c:v libx265 -crf 28 output.mp4",
  },
});

const job = await client.jobs.wait(created.id);

if (job.status === "complete") {
  console.log(outputUrl(job)); // signed download URL
}
```

`jobs.create` returns a `waiting` job. `jobs.wait` polls until the job reaches a terminal status (`complete`, `failed`, or `cancelled`) and returns it. The rest of this page covers the full job surface, the other resources, and client config.

## Jobs

The `jobs` resource is the core of the SDK. It creates jobs, polls them, reads their output, and lists past runs. Every method takes an optional `{ signal }` for [cancellation](#config-errors-and-retries).

### Create a job

`jobs.create` submits a job and returns the created job with `status: "waiting"`.

```ts
const created = await client.jobs.create({
  type: "ffmpeg",
  params: {
    command: "ffmpeg -i https://example.com/in.mp4 -c:v libx265 output.mp4",
  },
});

console.log(created.id, created.status); // "job_abc123" "waiting"
```

`type`, `inputs`, and `params` are job-type-specific. See [Job types](/jobs/overview) for each schema. Pass `idempotencyKey` to make retries safe: replaying the same key returns the original job instead of creating a second.

```ts
await client.jobs.create({
  type: "ffmpeg",
  params: { command: "ffmpeg -i in.mp4 out.mp4" },
  idempotencyKey: "render-2026-06-22-batch-7",
});
```

### Get, list, and paginate

`jobs.get` fetches one job by id. `jobs.list` returns one page plus pagination meta, filtered by `status`, `type`, `limit`, and `page`. `jobs.listAll` is an async iterator that walks every page for you.

```ts
const job = await client.jobs.get("job_abc123");

const page = await client.jobs.list({ status: "complete", limit: 20 });
console.log(page.data);       // Job[]
console.log(page.meta.total); // total matching jobs
console.log(page.meta.page);  // current page

for await (const job of client.jobs.listAll({ status: "failed" })) {
  console.log(job.id, job.type);
}
```

Use `list` for paginated UI. Use `listAll` for batch scripts that process the full history.

### Wait for completion

`jobs.wait` polls a job until it reaches a terminal status and returns it.

```ts
const job = await client.jobs.wait("job_abc123", {
  timeout: 600_000,  // give up after 10 min (default 300000)
  interval: 2_000,   // poll every 2s (default 2000)
  onProgress: (j) => console.log(j.status, "progress" in j ? j.progress : 0),
  signal: controller.signal,
});
```

`onProgress` fires on every poll with the latest job. If the job does not finish before `timeout`, `wait` throws. Pass a `signal` to abort the loop early.

### Cancel

`jobs.cancel` stops a `waiting` or `dispatched` job server-side and returns the updated job.

```ts
const job = await client.jobs.cancel("job_abc123");
console.log(job.status); // "cancelled"
```

### Read the output

A job is a discriminated union on `status`. The `output` field exists only when `status === "complete"`, and `error` only when `status === "failed"`. Narrow on `status` before reading either.

```ts
const job = await client.jobs.wait("job_abc123");

if (job.status === "complete") {
  // job.output is available here
} else if (job.status === "failed") {
  console.error(job.error.code, job.error.message);
}
```

The output and file types are:

```ts
type Output = {
  data: unknown | null;        // job-type-specific JSON, or null for file jobs
  file: OutputFile | null;     // headline file or .m3u8/.mpd manifest, null for sets
  files: OutputFile[];         // every file the job produced
  expiresAt: number | null;    // Unix ms URL expiry, set when files is non-empty
};

type OutputFile = {
  url: string;                 // ready-to-fetch, time-limited URL
  path: string;                // path within the job output
  type: "video" | "image" | "audio" | "captions" | "playlist" | "data" | "other";
  size: number;                // bytes
  meta?: { format?: string; width?: number; height?: number; durationMs?: number };
};
```

**The headline URL.** `outputUrl` returns the single result URL: the one output file, or the playlist manifest for an HLS/DASH stream. It returns `undefined` for a data-only job, a pure file set, or any non-complete job.

```ts
import { outputUrl } from "@rendobar/sdk";

const url = outputUrl(job);
if (url) console.log(url);
```

**Every file.** For jobs that emit many files (image sequences, HLS segments, a resolution ladder), iterate `output.files`.

```ts
if (job.status === "complete") {
  for (const f of job.output.files) {
    console.log(f.type, f.path, f.size, f.url);
  }
}
```

**Structured data.** For jobs that compute JSON (probe results, detections, transcripts), read `output.data` with `jobData<T>`. It returns `T | null`. `T` is your claim about the shape, so validate it yourself if the input is untrusted.

```ts
import { jobData } from "@rendobar/sdk";

type Metadata = { format: string; durationMs: number };

const meta = jobData<Metadata>(job);
if (meta) console.log(meta.durationMs);
```

**The failed-job shape.** A `failed` job carries `error`:

```ts
type JobError = {
  code: string;        // machine-readable error code
  message: string;     // human-readable message
  detail: string | null; // provider stderr tail (e.g. ffmpeg), or null
  retryable: boolean;  // true when retrying the same job may succeed
};
```

### Download, logs, and types

`jobs.download` returns the raw `Response` for the job's headline output, so you can stream it to a file or buffer it. `jobs.logs` returns the stored execution log entries. `jobs.types` lists the job types available to your org, with their schemas.

```ts
import { writeFile } from "node:fs/promises";

const res = await client.jobs.download("job_abc123");
await writeFile("output.mp4", Buffer.from(await res.arrayBuffer()));

const logs = await client.jobs.logs("job_abc123");
const types = await client.jobs.types();
```

## Other resources

Beyond jobs, the client exposes resources for uploads, batches, billing, webhooks, and realtime. Every method takes an optional `{ signal }`.

### Uploads

`uploads.create` uploads file content and returns a ready `Asset`. It runs the full `/assets` flow (init, presigned PUT or parallel multipart, complete) in one call. Reference the returned `asset.url` as a job input, and the API resolves it to the file at dispatch.

```ts
import { readFile } from "node:fs/promises";

const bytes = await readFile("clip.mp4");
const asset = await client.uploads.create(bytes, {
  filename: "clip.mp4",
  persist: true,                              // keep past the 24h auto-delete
  onProgress: (p) => console.log(`${p.loaded}/${p.total}`),
});

await client.jobs.create({
  type: "ffmpeg",
  inputs: { source: asset.url },
  params: { command: "ffmpeg -i {source} -c:v libx265 output.mp4" },
});
```

Uploads are ephemeral by default and auto-delete after 24 hours. Pass `persist: true` to keep an asset.

### Batches

`batches.create` submits many jobs in one request. Each entry takes the same shape as `jobs.create`. It returns the batch id, the job count, and every job id. Wait on the individual `jobIds` with [`jobs.wait`](#wait-for-completion).

```ts
const batch = await client.batches.create({
  jobs: [
    { type: "ffmpeg", params: { command: "ffmpeg -i a.mp4 a.webm" } },
    { type: "ffmpeg", params: { command: "ffmpeg -i b.mp4 b.webm" } },
  ],
});

console.log(batch.batchId, batch.jobCount, batch.jobIds);
```

### Billing

The `billing` resource reads your org's balance, usage, and transactions. `state` returns the current balance and plan, `usage` summarizes spend over a date range, and `transactions` is a paginated ledger.

```ts
const state = await client.billing.state();
const usage = await client.billing.usage({ start: "2026-06-01", end: "2026-06-30" });
const txns = await client.billing.transactions({ page: 1, limit: 50 });
```

### Webhooks

`webhooks.create` registers an endpoint that Rendobar calls when a job finishes.

```ts
const endpoint = await client.webhooks.create({
  name: "prod-renders",
  url: "https://example.com/hooks/rendobar",
  subscribedEvents: ["job.completed", "job.failed"],
});
```

Verify every incoming webhook before trusting it. `verifyWebhookSignature` is a standalone, zero-dependency export from `@rendobar/sdk/webhooks`. It runs in any runtime with Web Crypto (Node 18+, Deno, Workers, browser). Read the signature from the `X-Rendobar-Signature` header. The comparison is timing-safe, and it returns a `Promise<boolean>`.

```ts title="handler.ts"
import { verifyWebhookSignature } from "@rendobar/sdk/webhooks";

export async function POST(req: Request): Promise<Response> {
  const body = await req.text();
  const signature = req.headers.get("X-Rendobar-Signature") ?? "";

  const valid = await verifyWebhookSignature(body, signature, process.env.RB_WEBHOOK_SECRET!);
  if (!valid) return new Response("invalid signature", { status: 401 });

  const event = JSON.parse(body);
  // handle event
  return new Response("ok");
}
```

### Realtime

`realtime.connect` opens a WebSocket and streams org events. `realtime.subscribeJob` narrows the stream to one job. `connect` also takes `onLive` (replay finished, now live) and `onResync` (buffer overflowed, do a full refresh).

```ts
const sub = client.realtime.subscribeJob("job_abc123", {
  onProgress: (e) => console.log(e.progress),
  onStep: (e) => console.log(e.step),
  onComplete: (e) => console.log("done", e.status),
});

sub.unsubscribe();
```

<Warning>
  Realtime needs session-cookie auth, not API keys. It works in first-party browser code where the auth cookie is present. API-key users poll with [`jobs.wait`](#wait-for-completion) instead.
</Warning>

Every response and param type is exported from `@rendobar/sdk` as a named `type`.

```ts
import type { Job, Output, OutputFile, BillingState, WebhookEndpoint, Asset } from "@rendobar/sdk";
```

## Config, errors, and retries

`createClient` accepts these options. Only `apiKey` (or cookie auth) is required.

| Option | Type | Default | Purpose |
|---|---|---|---|
| `apiKey` | `string` | — | API key prefixed `rb_`. Required for server-side use. |
| `baseUrl` | `string` | `https://api.rendobar.com` | API origin. Override for a self-hosted or staging endpoint. |
| `timeout` | `number` | `30000` | Per-request timeout in milliseconds. |
| `maxRetries` | `number` | `2` | Max automatic retries for 429 and 5xx responses. |
| `orgId` | `string` | — | Default org, sent as `X-Org-Id`. Use when a key spans multiple orgs. |
| `debug` | `boolean` | `false` | Log request metadata to `console.debug`. |
| `fetch` | `function` | — | Custom `fetch` for testing or a special runtime. |
| `credentials` | `RequestCredentials` | — | Standard fetch credentials mode. Use `"include"` for cookie auth. |

### Authentication

Pass an API key for server-side use. For first-party browser code, set `credentials: "include"` and omit `apiKey` so the browser sends the auth cookie. API-key auth covers every REST method. Realtime needs cookie auth, so API-key users poll with `jobs.wait`.

```ts
const server = createClient({ apiKey: "rb_YOUR_KEY" });
const browser = createClient({ credentials: "include" });
```

### Errors

Every failed request throws an `ApiError`. Narrow with `isApiError` and switch on `error.code`. `ApiError` carries `code`, `statusCode`, `message`, optional `details`, and `retryAfter` (set on `RATE_LIMITED`).

```ts
import { isApiError } from "@rendobar/sdk";

try {
  await client.jobs.create({ type: "ffmpeg", params: { command: "ffmpeg -i in.mp4 out.webm" } });
} catch (err) {
  if (isApiError(err)) {
    console.log(err.code, err.statusCode, err.message);
    if (err.code === "RATE_LIMITED") {
      console.log(`retry after ${err.retryAfter}s`);
    }
  }
}
```

The `code` values are `UNAUTHORIZED`, `FORBIDDEN`, `VALIDATION_ERROR`, `INSUFFICIENT_CREDITS`, `RATE_LIMITED`, `NOT_FOUND`, `CONFLICT`, and `INTERNAL_ERROR`.

A job that fails during execution is not an HTTP error. It returns a `failed` job with `job.error`, the four-field `JobError` shown under [Read the output](#read-the-output).

### Retries and cancellation

The client retries transient failures automatically, up to `maxRetries` (default 2) with exponential backoff (500ms, then 1s).

| Response | Behavior |
|---|---|
| `429` | Retried, respecting the `Retry-After` header |
| `500`, `502`, `503`, `504` | Retried with backoff |
| Other 4xx | Thrown immediately, no retry |

Every method takes an optional `signal` (an `AbortSignal`). Abort it to cancel an in-flight request or a `jobs.wait` poll loop. Aborting throws an `AbortError` and cancels the client request only. To cancel the job itself on the server, call [`jobs.cancel`](#cancel).

```ts
const controller = new AbortController();
setTimeout(() => controller.abort(), 5000);

const job = await client.jobs.wait(created.id, { signal: controller.signal });
```
